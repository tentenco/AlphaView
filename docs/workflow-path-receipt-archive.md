# 工作流路徑收據封存與預檢

方法版本：`alphaview-workflow-path-receipt-archive-v1`；封存格式版本：`1`。

完整封存包含同一個 paper 帳戶跨工作流保存的所有 `path_validation` 與 `path_costs` 收據。路徑比較、CSCV 與成本研究使用的原始證據可以下載為一份可攜 JSON，再送回本機做唯讀相容性預檢。這不會重建路徑、重跑決策或成本情境，也不讀取行情。

## 端點與完整集合

- `GET /api/paper/accounts/{account_id}/workflow-path-receipt-archive`
- `POST /api/paper/accounts/{account_id}/workflow-path-receipt-archive/preflight`

帳戶識別必須是 32 位小寫十六進位字串，且帳戶存在。POST 以 `Content-Type: application/json` 傳入原始 UTF-8 封存文字。

GET 在單一 query-only 一致快照中讀取完整帳戶集合，不使用歷史頁面的分頁或單一工作流篩選。集合成員由 `account_id` 的精確儲存位元組決定，必須等於要求的 ASCII 識別。BLOB 儲存格若位元組相同仍納入封存，但其非文字型別使原始收據不可驗證；不改寫帳戶識別或移到其他帳戶。

快照內同時取得帳戶版本、輸入版本、完整集合、本機同識別紀錄與容量。`as_of` 一律取自 `sessions.latest_completed_session()`；交易日在請求期間改變會回傳 409，避免發布混合狀態。兩個端點沒有 DDL、資料寫入、還原或刪除。

## 原始內容與校驗

固定保留九欄：`id`、`account_id`、`run_id`、`kind`、`created_at`、`engine_version`、`request_json`、`content_fingerprint`、`payload_json`。每格保留 `storage_type`、`encoding`、`byte_length`、`sha256`、`content`。

| SQLite 型別 | 封存表示 |
| --- | --- |
| 合法 UTF-8 TEXT | 原始文字與 `utf-8` 編碼標記 |
| 非法 UTF-8 TEXT | 原位元組的 `base64`，仍標記 TEXT 型別 |
| BLOB | 原位元組的 `base64`，保留 BLOB 型別 |
| INTEGER | 有號 64 位元整數的標準十進位字串 |
| REAL | 大端序 IEEE754 64 位元的 `base64`，保留負零或非有限位元模式 |
| NULL | 明確 `null`、零位元組 |

REAL 的非有限位元模式只作不可解讀證據的原始內容保留，不成為 JSON 數字或可用研究數值。損壞 JSON、非法編碼與缺值不會被取代、修復、補零或截短。UI 的「原始內容完整」與「完整性可核對」分開計數。

每格雜湊核對其原始位元組，每列 `row_checksum` 核對完整型別化紀錄；`set_fingerprint` 對排序後的列校驗值多重集合取雜湊，保留重複列數量；`checksum` 核對封存除 checksum 本身外的全部內容。Canonical JSON 使用 sorted keys、UTF-8、無多餘空白與有限數字。下載使用伺服器回應原文，不經瀏覽器重新序列化。

校驗值不是簽章或來源真實性證明。完整集合的宣告只描述當次本機匯出快照，不能單靠外部檔案證明來源沒有整批刪除歷史；預檢另外呈現目前本機集合是否改變。

## 預檢涵蓋的範圍

預檢檢查嚴格 JSON、重複鍵、非有限數字、UTF-8、孤立 surrogate、封存版本、型別編碼、逐格雜湊、列與集合校驗、完整筆數，以及封存與目標帳戶的精確綁定。

原始收據會重新核對規範化保存請求、帳戶／工作流／kind、完整封裝、原始內容指紋、來源綁定、證據指紋與理解範圍內的資料形狀。路徑包含設定指紋、決策、日期、覆蓋計數、資產曲線、事件與持股形狀。成本收據另外檢查完整基準、每一組請求費用／滑價配對、情境狀態與覆蓋計數。方法版本與方法說明必須受支援。這些檢查不重新計算數值結果。

無法驗證的列仍完整保留，但使整份預檢不相容。即使原始損壞內容與本機完全相同，或所有封存校驗值已被重新計算，也不能成為可用證據。不同內容卻使用相同識別、重複封存識別、異帳戶內容與不支援的方法都會阻擋。

原始研究狀態與相容性分開：`evaluated`、`incomplete`、`unavailable` 保留原意。原始不可用路徑與部分情境失敗的成本收據仍可能具有完整、可核對的證據，不能改寫成研究通過。有效歷史收據即使帳戶、工作流、交易日或工作區輸入已變更，仍可相容；來源當期狀態另列原因，不刷新原值。

每筆預檢顯示本機已有完全相同紀錄、尚無紀錄、同識別內容衝突或無法核對。介面另外列出帳戶／全域用量、剩餘容量、缺少識別數與計入這些紀錄後的預估筆數；未知識別使預估值為 `null`，UI 顯示 `—`，不以 0 代替。

## 上限與回應

| 限制 | 行為 |
| --- | --- |
| 每帳戶 50 筆、全域 250 筆 | GET 超限拒絕整份；預檢估算新增缺少紀錄是否超限 |
| 原始收據 payload 2 MiB、保存請求 16 KiB | 超限原始收據不可驗證，原值仍按完整封存上限保留 |
| 完整封存與 POST 原始請求 32 MiB | 超限回傳 413，不回傳部分集合或省略任何儲存格 |
| 媒體型別錯誤 | 415 |
| 帳戶不存在／識別格式不符 | 404／422 |
| 請求期間已完成交易日改變 | 409 |
| 無效 JSON、封存不相容 | 200，`verdict: blocked` 與明確原因 |

不自動刪除收據、不騰出容量、不放寬既有上限。預估容量是唯讀說明，不代表匯入承諾。相同本機收據不重複計入缺少筆數。

## 介面與生命週期

`WorkflowPathReceiptArchive` 接受 `accountId`、`accountVersion` 與翻譯函式 `t`。使用者明確按準備才讀取完整封存，明確按下載才保存原始文字。檔案選取與貼上只更新草稿，按預檢才送至本機 API；不會自動匯入。32 MiB 與嚴格 UTF-8 限制在讀檔時先檢查，JSON 結構交由伺服器核對，因此重複鍵不會被瀏覽器解析時消掉。

帳戶或版本改變會取消請求，撤下舊下載與預檢結果並保留未送出的草稿。修改草稿或換檔會立即取消舊預檢；檔案不合法時也不保留舊的相容標示。同步請求鎖避免連點重送，晚回應不能覆蓋新條件。空草稿禁止預檢，長雜湊、檔名和按鈕在窄畫面換行。

逐筆預檢使用 `ArchivePreflightRecords`：每頁 25 筆，可選「全部／相容／不可用」並用 ID 子字串搜尋，不改原紀錄排序、不合併重複 ID。摘要中的長 ID 縮成前 12、後 8 字元；完整原值保留在 title 與原生 details 展開內容，未知識別明確標示，不推測或補值。

清單顯示符合／全部已回傳筆數、目前範圍與頁次。相容篩選只看各列原本的 `compatible`，所以「結構相容但原始研究不可用」仍保留原研究狀態。整份受阻結論、所有整份錯誤、完整 coverage、來源計數與帳戶／全域容量永遠不受篩選影響；選「相容」或搜尋零筆，不會使封存變成相容。

搜尋是不分大小寫的字面 ID 子字串比對，不改寫 ID、原 payload 或任何封存 bytes。篩選／搜尋變更回到第一頁，新接受的報告物件重設清單控制，相同報告的無關重繪保留選擇；不存在的頁面不會顯示。鍵盤可操作原生選單、搜尋、分頁按鈕與 details，390px 寬改為直向篩選控制。這些操作沒有額外 API、storage 或 hash 寫入，原始 JSON 草稿、下載與生命週期防護維持原樣。
