# 執行研究不可變回條

方法版本：`alphaview-execution-study-receipt-v1`。回條保存既有 `volume_day`（成交量 DAY）、`limit_day`（開盤限價 DAY）、`open_gtd`（最多五個交易日開盤 GTD）研究的完整原始結果。三種研究的計算方法與既有提案重播語意不變。

研究完後可以明確按「保存研究回條」。歷史清單與細節均需使用者點擊才讀取，沒有背景保存或自動重新計算。即使目前草稿或來源不再允許新增回條，仍可檢閱原來保存的研究。每份回條保留完整設定、逐筆訂單／每日證據、覆蓋計數、缺值、原因、方法版本和來源指紋；`null` 保持未知，明確的零情境仍是零。

## 原始位元組與指紋

保存請求不接受用戶提交的研究 payload。伺服器以原研究模組、同一個 SQLite 讀取快照重新計算，使用與既有 HTTP 端點相同的 `JSONResponse` 編碼，核對 `expected_raw_evidence_sha256`。這是**完整原始 UTF-8 HTTP JSON 位元組**的 SHA-256，與 GTD 結果內嵌的 `evidence_fingerprint` 是不同識別。研究結果沒有新增時間戳或剔除欄位以求匹配；既有回應中的每個欄位均參與核對。回條自身的 `created_at` 在回條 envelope 中，獨立於原研究內容。

資料庫只保存一份完整 envelope：第一個 `evidence` 值是直接嵌入的原始研究 JSON，沒有 parse/stringify 後再輸出的表示損失，也沒有重複存放 raw 與 parsed 副本。每次讀取會核對完整回條位元組指紋、原始研究位元組指紋、嚴格請求、帳戶與提案識別、來源及方法綁定；GTD 另核對其內嵌計算指紋。非有限數字、重複 JSON key、損壞 metadata 或不相符內容一律標為無法驗證，不能下載成有效證據。

畫面分開顯示「完整回條指紋」與「原始研究 JSON 指紋」。原始研究下載回傳最初保存的研究位元組；完整回條下載回傳資料庫保存的完整 envelope 位元組。兩者均在瀏覽器核對 SHA-256、ETag、回條指紋及帳戶／提案識別，保留 `1.0`、`-0.0`、指數、Unicode、未來欄位與 `null`。畫面中格式化的 JSON 僅供閱讀，不是下載內容。

## 保存與一致性

先在讀取快照重算並核對已檢閱結果，隨後在 `BEGIN IMMEDIATE` 內再核對帳戶版本和政策、完整保存提案紀錄的指紋、輸入 revision、最新完成交易日與研究／回條方法版本。任何一項改變會回 409，不保留半份回條。帳戶限額／執行政策／標的政策亦受綁定；沒有改變帳戶、提案、持股、帳本、委託或 input revision 的研究保存副作用。

相同帳戶、提案、種類與正規化保存請求會得到同一個回條 ID。重試若找到可驗證的原回條，直接重播原始內容，即使目前來源或方法已改變也不重算、不覆寫。損壞的同識別紀錄不能藉重試修補。這種歷史重播不使舊證據恢復為目前證據。

`currentness` 描述**研究計算當時的來源上下文**與讀取時是否相符，並非原訊號提案是否當期。研究本來就使用前日保存股數與後續已完成交易日，因此原提案的 `source.current` 常為 false；兩者分開顯示。來源改變後，歷史結果仍可下載原值，當前性會列出輸入、交易日、帳戶政策、提案或方法改變原因。讀取只檢查 metadata，不重新生成研究值。

## API 與保留限制

### 本機歷史瀏覽

按「讀取研究回條」後，畫面會依目前帳戶、提案與研究種類讀取完整歷史。既有 API 每批最多 20 筆，因此一次明確讀取最多請求三批，最多組成 50 筆。所有批次的總筆數、最新完成交易日與 input revision 必須相同，帳戶、提案、種類及每批筆數均需吻合，回條 ID 不可重複；任何一批失敗或來源變更都不發布半份新清單。先前已完整讀取的清單若仍在相同上下文，會保留供檢閱並顯示這次讀取錯誤。

完整清單讀取後，可依「全部／可驗證／完整性不可用」篩選、搜尋回條 ID，並以每頁最多 10 筆瀏覽。ID 搜尋忽略英文字母大小寫與前後空白；這些控制只處理已讀取的本機清單，不讀取 API、不保存、不重新計算。研究種類由原研究區塊固定，不另設混合種類篩選。變更篩選、搜尋或成功重新讀取歷史會回到第一頁；切換帳戶、提案或研究種類也會清除篩選與搜尋。

完整歷史筆數、可驗證筆數、完整性不可用筆數及來源狀態未知筆數固定顯示於篩選外；未知狀態保留為未知，篩選不會改變任何來源判定或執行資格。已選取回條的細節與原始下載不因其清單列被篩選隱藏而消失，研究比較也持續使用完整清單。搜尋無結果只表示目前篩選沒有符合項目，不表示沒有歷史研究。

### 端點

基底路徑：`/api/paper/accounts/{account_id}/proposals/{proposal_id}/study-receipts`，帳戶與提案 ID 必須為 32 位小寫十六進位。回條 ID 與 SHA-256 必須為 64 位小寫十六進位。

| 操作 | 契約 |
| --- | --- |
| POST 基底 | `{kind, request, expected_evidence_engine_version, expected_raw_evidence_sha256}`；`request` 使用對應既有研究的嚴格完整請求。新保存 201，完全相同的歷史重播 200。 |
| GET 基底 | 可選 `kind`，`limit` 1–20（預設 20），`offset` 0–250；帳戶及提案範圍內列出回條。 |
| GET `/{id}` | 不可變細節、完整 parsed envelope、完整性與獨立當前性。 |
| GET `/{id}/evidence.json` | 原研究 JSON 位元組；必須帶 `expected_content_fingerprint`（完整回條指紋）。 |
| GET `/{id}/receipt.json` | 完整回條 envelope 位元組；同樣必須帶完整回條指紋。 |

每帳戶最多 50 份、全工作區 250 份、完整回條最多 2 MiB、完整保存請求最多 16 KiB。滿額或超過大小就拒絕，不截短、不覆寫、不自動刪除；沒有匯入、刪除或保留期限 API。所有 GET 使用 `@store.snapshot_read`，不初始化 schema、不寫入。host 初始化才呼叫 `ensure_schema(db)`。

前端共用元件 `ExecutionStudyReceipts` 接受 `kind/accountId/proposalId/accountVersion/request/evidence/rawEvidence/enabled/t`；`request` 應為原回應中的完整正規化請求，`rawEvidence` 為已接受的 `response.text()`。不需要把原訊號提案 `source.current` 當作保存資格。父元件用自己目前的研究結果資格設定 `enabled`，來源變更要清除當前 `evidence/rawEvidence`。元件會在帳戶、提案、設定、來源、enabled、pagehide 或 unmount 時中止待處理操作，避免晚到回應與重複點擊；不管理或清除父層未送出的參與率、限價、GTD 日期草稿。

## 這不是什麼

回條不是實際成交、開盤流動性證明、限價日內路徑、券商狀態、交易授權或提案就緒閘。全日量仍只是事後容量代理；GTD 未完成日期或缺少中途必要證據仍為未知。保存不可用研究只代表保留它當時的缺口，不把不可用狀態改為通過。沒有任何供應商、模型、券商呼叫或實際委託。
